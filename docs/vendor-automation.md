# Public vendor enrollment and CI promotion

The checked-in `vendor.lock.json` records each allowlisted source and LICENSE
file with its upstream commit, Git blob and SHA-256. Checked-in copies support
offline local tests. `vendor/* -text` retains the exact upstream bytes on
Windows and Unix, including the GHI module and its LICENSE.

GHI is enrolled as an unused module. `yourself.py` and the CLI do not import or
call it; runtime dependencies and behavior are unchanged. CI loads the enrolled
module under `python -S` to check loadability without site packages. That smoke
does not exercise GHI's GitHub operations or enforce the absence of import-time
I/O in future upstream versions.

## Bootstrap with the canonical tool

CI and local enrollment use the shared stdlib tool pinned at
`380d877cd85837f36cf6030d626ee8bb7dfa28cb`.

`enroll` verifies every existing destination against the lock before downloading
anything. An existing mismatch fails instead of being repaired. Only missing
destinations are downloaded from their locked commit and verified against their
Git blob and SHA-256 before placement; the lock is unchanged. This permits a new
source/LICENSE pair to be added without a consumer-specific bootstrap helper.
`materialize` can also restore mismatched locked files, so it serves a different
purpose from enrollment. Download or digest failure leaves missing enrollment
destinations uncreated; filesystem failures during placement can leave a partial
batch and are reported as errors. Create-only enrollment requires a filesystem
that supports hard links; it has no overwrite fallback.

## One resolved snapshot per workflow

The `resolve-vendor` job first checks all checked-in copies, then deliberately
removes only `vendor/gh_identity.py` and `vendor/gh_identity-LICENSE`. It runs
canonical `enroll`, validates the result as JSON, and checks the reconstructed
baseline offline. `vendor-enrollment.json` records that baseline enrollment;
it precedes any upstream promotion in the same run.

The job next removes and materializes all five locked source/LICENSE files.
Normal push/PR CI and the default `vendor-mode: update` dispatch then run
canonical `promote` once, validate the `vendor-promotion/1` JSON receipt, and
check the promoted bytes offline. Each upstream ref resolves once during
promotion. Every OS/Python job downloads this same `vendor-snapshot`, verifies
it offline, loads GHI under `python -S`, and runs the existing tests. Upstream
changes during the matrix cannot select different sources for different jobs.

`vendor-mode: locked` still exercises GHI enrollment and all-file locked
materialization, but skips promotion and does not include a promotion receipt
path in artifact uploads. It tests the recorded baseline. A successful promotion
with no upstream byte changes still emits a real receipt with empty
`changed_paths` and `promoted` lists. Unchanged selected bytes do not churn
baseline pins; each source/LICENSE entry retains its own verified identity.

The resolved lock, five exact vendor files and enrollment result are preserved
before and after tests, including failures. The parent stager derives file
membership from the lock, includes the enrollment receipt as runtime evidence,
and emits `vendor-evidence.json`. Candidate snapshots also retain an available
promotion receipt. Unlocked files such as generated bytecode are excluded. Both modes preserve the existing JUnit/native and controlled-child
evidence. A failing vendor command stays nonzero even when its JSON output is
piped through `tee`; later checks cannot mask that failure.

## Local use

An agent can use the same canonical CLI after adding complete lock entries:

```bash
set -euo pipefail
git clone https://github.com/myon-bioinformatics/myon-bioinformatics.git .vendor-sync-tools
git -C .vendor-sync-tools checkout --detach 380d877cd85837f36cf6030d626ee8bb7dfa28cb
python -S .vendor-sync-tools/vendor_sync.py enroll --manifest vendor.lock.json | tee vendor-enrollment.json
python -S .vendor-sync-tools/vendor_sync.py check --manifest vendor.lock.json
# Restore missing or mismatched locked files when restoration is intended:
python -S .vendor-sync-tools/vendor_sync.py materialize --manifest vendor.lock.json
python -S .vendor-sync-tools/vendor_sync.py promote --manifest vendor.lock.json | tee vendor-promotion.json
python -S -m json.tool vendor-promotion.json > /dev/null
python -S .vendor-sync-tools/vendor_sync.py check --manifest vendor.lock.json
python -m pytest
```

Offline local pytest uses checked-in copies and does not download sources.
Public source and metadata downloads are anonymous. API 403/429 uses a temporary
public Git snapshot with credential helpers disabled; failures stay nonzero.
The updater remains pinned at its reviewed full SHA. Both CI checkouts disable
persisted credentials. These commands and workflows do not commit, push, open
PRs, or write results back to main. An artifact's exact lock can be materialized
later to reproduce the sources tested in that run.


## Lock-derived evidence staging

Vendor artifact membership is now derived exclusively by the parent
`vendor_stage.py`, checked out with `vendor_sync.py` at full commit
`380d877cd85837f36cf6030d626ee8bb7dfa28cb`. Workflow uploads point to its generated
directory; adding a locked source or LICENSE needs no upload path-list edit.
Artifact names and repository-relative paths inside each artifact are preserved.
`vendor-evidence.json` is additional metadata with byte hashes and separate
locked/candidate, runtime receipt, and legacy projection classifications.

Staging runs even after a failed test, verifies every locked byte, and fails
nonzero on missing or modified members. It does not certify tests or promotion.
Locked runs exclude promotion receipts; candidate runs include one when present.
Legacy projection formats, when present, remain consumer-owned outputs of the
lock. Exact source pins, LICENSEs, test-only dependencies and Pages/MCP/runtime
behavior are unchanged. Central topology intent is owned by the parent's
`vendor-consumers.json`; recommended baselines belong to `vendor-catalog.json`;
this consumer's lock remains the authority for adopted bytes.
